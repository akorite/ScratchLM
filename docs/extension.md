# Bonsai storage extension

Load `extension/loader.js` as a **custom unsandboxed extension** in TurboWarp (Extensions → Custom Extension, using a URL served by a local web server or a trusted hosted copy). Unsandboxed extensions have full page and VM access: only load source you trust. Use TurboWarp, not the Scratch website. Create a package using `tools/package_model.py` as described in [model-format.md](model-format.md); the package is selected locally and is not uploaded by this extension. Verify its published checksum independently before use. Select the file with the `select Bonsai package` block and wait for package status `ok`; a failed selection reports `error: ...`. Cancelling the file picker leaves the current package unchanged.

The loader checks the package header, manifest, tensor shapes and ranges, but does not authenticate the package or scan the entire payload. Package only the verified model with the supplied packer. The package codec reporter is `raw` or `bslut4`; the bytes are copied unchanged. Metadata and tensor indices are **1-based**. Metadata value returns a scalar or JSON for an array; tensor fields include `type_id`, `dimensions` (JSON), `offset`, and `length`. Metadata keys can be enumerated with the count and key blocks; tensors with the count and name blocks. For large tokenizer arrays, JSON reporters can be large.

## Transfers

Create ordinary Scratch lists before loading. Supply their **variable IDs**, not their displayed names: find IDs in the project's `project.json` list definitions, or in the project's block generator. IDs resolve in the calling sprite first, then the stage, just as the VM resolves variables. Different sprites cannot address each other's local lists. A group request takes a tensor name, zero-based group start and whole-group count, two distinct list IDs (packed bytes and scale words), and a caller-chosen request ID. A dense request takes a tensor name, zero-based float start and element count, one list ID, and a request ID. Both command blocks wait for their read to finish. Use a separate script to cancel an outstanding request.

Each successful group contributes 32 numeric byte items and one unsigned numeric little-endian 16-bit scale word, in group order. Each dense item is the numeric value of a little-endian F32. No ternary recoding, FP16 decoding, neural arithmetic, or inference is performed in JavaScript. Zero-length requests at the end of a tensor succeed and clear their destination lists; a range beyond the end fails rather than truncating. Offsets and counts must be nonnegative safe integers. The maximum is `floor(4194304 / 34)` groups or `1048576` floats; for a nominal byte budget request `floor(budget / 34)` groups. Smaller chunks may be needed for responsiveness.

On success the complete destination contents are replaced, retaining the VM list variable objects, and status becomes `ok`. The copied reporter counts groups or floats, not bytes; multiply groups by 34 for file bytes. On failure status is `error`, copied is zero, and the error reporter describes the failure; destination lists are untouched. Other statuses are `pending`, `cancelled`, `stale`, and `unknown`. The latest request using an ID replaces that ID's previous result. A later pending request targeting the same list makes the earlier request stale, even with a different ID. Cancellation, changing package, deleting/replacing the target or list, a short read, and stale completions cannot publish a partial result. Cancellation cannot interrupt a synchronous list copy already underway. Request IDs are retained for status reporting; reuse IDs in long-running programs.

Do not modify a destination list while its request is pending. The extension binds list objects and target before asynchronous I/O and checks they still belong to that target before publishing, but does not prevent Scratch scripts from changing list contents during a read. Once a tile is resident, its Scratch computation does not require the extension; future loads do. Schedule computation in bounded tiles with yields outside warp, measure the actual copy duration, and reduce tile size if needed. The 4 MiB ceiling is a safety bound, not a latency guarantee. Actual compiled TurboWarp behavior and target-hardware throughput require separate integration measurements.

The focused Node transport tests can be run from the repository root with `node --test tests/transport/*.test.js`; they exercise File/Blob reads and VM-shaped list variables, not the compiled TurboWarp runtime.
