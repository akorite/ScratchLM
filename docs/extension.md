# Bonsai storage extension

Load `extension/loader.js` as a **custom unsandboxed extension** in TurboWarp (Extensions → Custom Extension, using a URL served by a local web server or a trusted hosted copy). Unsandboxed extensions have full page and VM access: only load source you trust. Use TurboWarp, not the Scratch website. Create a package using `tools/package_model.py` as described in [model-format.md](model-format.md); the package is selected locally and is not uploaded by this extension. Verify its published checksum independently before use. Select the file with the `select Bonsai package` block and wait for package status `ok`; a failed selection reports `error: ...`. Cancelling the file picker leaves the current package unchanged.

The loader checks the package header, manifest, tensor shapes and ranges, but does not authenticate the package or scan the entire payload. Package only the verified model with the supplied packer. The package codec reporter is `raw`, `bslut4`, or `bslut5`; the bytes are copied unchanged. Metadata and tensor indices are **1-based**. Metadata value returns a scalar or JSON for an array; tensor fields include `type_id`, `dimensions` (JSON), `offset`, and `length`. Metadata keys can be enumerated with the count and key blocks; tensors with the count and name blocks. For large tokenizer arrays, JSON reporters can be large.

## Chat view

With the prompt-to-text project loaded, the extension opens a browser chat window
with a multiline composer, local conversation display, model picker and Stop control.
It reads the project's `BS ui phase`, `BS layer`, `BS step`, prompt length, head-scan
row count and decoded text; it does not compute model outputs or simulate progress.
Send sets the prompt and starts the existing Scratch generation loop. Each send
resets the sequence; displayed previous turns are not fed back to the model.
Closing the view keeps inference running; use Stop to interrupt it. The view is
absent in headless environments and is removed when the project/runtime is replaced.

## Transfers

Create ordinary Scratch lists before loading. Supply their **variable IDs**, not their displayed names: find IDs in the project's `project.json` list definitions, or in the project's block generator. IDs resolve in the calling sprite first, then the stage, just as the VM resolves variables. Different sprites cannot address each other's local lists. A group request takes a tensor name, zero-based group start and whole-group count, two distinct list IDs (packed bytes and scale words), and a caller-chosen request ID. A dense request takes a tensor name, zero-based float start and element count, one list ID, and a request ID. A request whose range falls inside the loader's read-ahead window copies and returns **synchronously** in the same block step; a request that misses the window waits for one refill, then publishes. Use a separate script to cancel an outstanding request — cancellation cannot interrupt a synchronous copy already underway.

A metadata-string request copies one named metadata string array, such as `tokenizer.ggml.tokens` or `tokenizer.ggml.merges`, into a list unchanged. It yields before publishing so it can be cancelled or superseded; the copy itself is synchronous. Its copied count is the number of strings. Missing keys and arrays containing non-strings fail without modifying the destination.

Each successful group contributes 32 numeric byte items and one unsigned numeric little-endian 16-bit scale word, in group order. Each dense item is the numeric value of a little-endian F32. No ternary recoding, FP16 decoding, neural arithmetic, or inference is performed in JavaScript. Zero-length requests at the end of a tensor succeed and clear their destination lists; a range beyond the end fails rather than truncating. Offsets and counts must be nonnegative safe integers. The maximum is `floor(4194304 / 34)` groups or `1048576` floats; for a nominal byte budget request `floor(budget / 34)` groups. Smaller chunks may be needed for responsiveness.

On success the complete destination contents are replaced, retaining the VM list variable objects, and status becomes `ok`. A synchronous copy completes before `status` can ever observe `pending`; a refill shows `pending` until it publishes. The copied reporter counts groups or floats, not bytes; multiply groups by 34 for file bytes. On failure status is `error`, copied is zero, and the error reporter describes the failure; destination lists are untouched. Other statuses are `cancelled`, `stale`, and `unknown`. The latest request using an ID replaces that ID's previous result. A later pending request targeting the same list makes the earlier request stale, even with a different ID. Cancellation, changing package, deleting/replacing the target or list, a short read, and stale completions cannot publish a partial result. Request IDs are retained for status reporting; reuse IDs in long-running programs.

The loader keeps a bounded read-ahead window (default 64 MiB) of package bytes. Selecting a package starts filling the window immediately; requests covered by it return in-block without a frame cost. When a served request nears the window tail, the loader prefetches the following window region, so sequential tensor scans refill at most once per window. A request larger than the window reads its range directly. Opening a new package discards the window and any prefetch. As an **extension side effect**, selecting a package sets the TurboWarp framerate to 250 (`runtime.setFramerate`), because the compiled scheduler's frame cost is what paces block execution. Keep the tab in the foreground: browser background-tab timer throttling clamps non-rAF timers toward 1 Hz, which stalls 250 fps pacing. Do not modify a destination list while its request is pending. The extension binds list objects and target before I/O and revalidates them after a refill before publishing, but does not prevent Scratch scripts from changing list contents during an asynchronous wait. Once a tile is resident, its Scratch computation does not require the extension; future loads do. Schedule computation in bounded tiles with yields outside warp. The 4 MiB ceiling is a safety bound, not a latency guarantee. Actual compiled TurboWarp behavior and target-hardware throughput require separate integration measurements.

The focused Node transport tests can be run from the repository root with `node --test tests/transport/*.test.js`; they exercise File/Blob reads and VM-shaped list variables, not the compiled TurboWarp runtime.
